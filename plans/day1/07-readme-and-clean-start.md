# D1-07 README 与全新启动验收规划

## 1. 文档职责

本文档只规划 D1-07“README 与全新启动验收”的目标、范围、任务、预期产物、风险和验收标准。

本文档不包含 README 成品、具体命令、配置内容、逐条操作教程或执行日志。上述内容只在用户明确要求执行 D1-07 后，于对话中按工程切片推进。

D1-07 是 Day 1 的最后一个阶段。完成本规划不代表 README 已创建，也不代表全新启动已经通过。

## 2. 阶段入口与当前事实

### 2.1 已满足的前置条件

- D1-01 至 D1-05 已形成工具链、三端脚手架、基础设施、配置示例和健康检查。
- D1-06 已建立一个最小 GitHub Actions Workflow。
- Web、Server、Agent 和基础设施四类本地质量门禁均已通过。
- GitHub Actions 四个作业已在同一次运行中全部通过。
- D1-06 修正已通过 PR #3 合并到 `develop`。
- 当前仓库没有根 `README.md`，因此尚不存在面向首次使用者的统一入口。

### 2.2 当前可复用的真实契约

- 根级与三端应用均已有 `.env.example`，真实 `.env` 不进入 Git。
- Web、Server 和 Agent 分别运行在 Windows；PostgreSQL、Redis、Qdrant 和 RustFS 运行在 Ubuntu VM 的 Docker Compose 中。
- Server 使用项目级 Maven Toolchains 选择 JDK 21，Windows 默认 Java 继续保持 17。
- Server 和 Agent 已区分存活与就绪；Web 通过配置校验、开发服务器响应和构建证明可用。
- 三端依赖分别由锁文件或 Maven Wrapper 约束，基础设施镜像由 Compose 固定。
- 本地质量入口与 CI 入口已经一致，D1-07 只引用它们，不再设计第二套检查方式。

### 2.3 已识别的文档风险

`docs/03-development-guide.md` 当前将本地启动描述为统一从 Windows PowerShell 开始，但既定运行拓扑要求 Compose 位于 Ubuntu VM。D1-07 必须在不改变运行架构的前提下明确操作位置；若执行验证确认开发指南存在歧义，只做与真实运行方式一致的最小修正。

## 3. 本步目标与原则

### 3.1 阶段目标

建立一个简洁的根 README，使第一次接触仓库的人能够：

1. 快速理解 Purple Nexus 当前是什么、由哪些模块组成。
2. 确认所需工具和 Windows / Ubuntu VM 的职责边界。
3. 从安全示例准备本地配置，而不提交真实地址或凭据。
4. 按正确顺序恢复依赖、启动基础设施与三个应用。
5. 通过已有健康入口判断“进程存活”和“系统就绪”。
6. 复用已有质量门禁完成提交前检查。
7. 正常关闭环境且不误删持久化数据。

随后从干净的项目状态仅依据 README 完成一次端到端启动验收，证明 Day 1 工程底座可以复现。

### 3.2 README 定位

根 README 是“首次进入项目的最短路径”，不是第二份开发指南或架构设计文档。

- README 保留首次启动必须知道的信息和最短操作路径。
- 详细环境变量职责、Git 规则和迁移规则链接到开发指南。
- 系统边界、产品范围和长期决策链接到对应文档。
- 依赖精确版本以构建文件、锁文件、Wrapper 和 Compose 为准，不在 README 重复维护。
- 不复制规划历史、执行日志或尚未实现的产品功能。

### 3.3 “全新启动”的验收定义

本阶段的“全新”指一份新的仓库检出，具备已声明的宿主工具，但不依赖原工作目录中的项目状态：

- 不存在三端已安装的项目依赖、构建产物或缓存产物。
- 不存在任何本地 `.env`。
- 不依赖全局 Maven、全局 Python 包、个人绝对路径或未记录的人工控制台配置。
- Ubuntu VM、Docker Engine、网络入口和基础工具作为已声明的前置环境存在。

该验收不要求重装操作系统、卸载全局工具、删除 Docker 镜像或销毁持久化卷。删除卷属于破坏性数据重置，不用于证明首次启动。

## 4. 范围边界

### 4.1 本阶段包含

- 创建根 `README.md`。
- 用简短内容说明项目定位、当前 Day 1 能力和 Monorepo 模块职责。
- 明确 Windows 应用与 Ubuntu VM 基础设施的运行位置。
- 记录前置工具、配置准备、依赖恢复、启动顺序、健康检查、质量检查和安全关闭。
- 标明 JDK 21 的项目级使用边界，不改变 Windows 默认 Java 17。
- 链接现有详细文档，避免在 README 重复维护同一结论。
- 从干净项目状态执行一次完整启动与关闭验收。
- 仅在验收暴露真实文档漂移时，最小修正 README 或现有开发指南。
- 形成一次可追踪的 D1-07 与 Day 1 验收结论。

### 4.2 本阶段不包含

- 新增业务页面、API、数据表、Agent 能力或业务测试。
- 修改三端构建配置、锁文件、Maven Toolchains 或质量工具。
- 新建或重构 GitHub Actions Workflow。
- 重新设计 D1-04 的基础设施或 D1-05 的配置与健康检查。
- 将 Web、Server 或 Agent 加入 Compose。
- 引入安装脚本、任务运行器、容器化开发环境或新的文档生成工具。
- 连接生产环境、部署到公网、配置域名、HTTPS、备份或监控。
- 在仓库中记录个人 VM 地址、本机 JDK 绝对路径或真实密钥。
- 为了“干净”而删除现有持久化卷、业务数据或用户环境。
- 把 Day 2 及以后的功能路线写成已经完成的能力。

## 5. README 内容规划

README 按首次使用者的阅读顺序组织：

| 区块 | 回答的问题 | 内容边界 |
| --- | --- | --- |
| 项目简介 | 这是什么 | 一段定位、当前骨架状态和主要技术栈 |
| 运行拓扑 | 各组件在哪里运行 | 三端应用、Ubuntu VM 基础设施及调用方向 |
| 仓库结构 | 应该从哪里找代码 | 只展示顶层和三个应用目录 |
| 前置条件 | 启动前需要什么 | 工具版本基线、VM 与网络前提、JDK 21 项目级约束 |
| 配置准备 | 哪些本地输入必须建立 | 四份示例文件的职责、安全边界和一致性要求 |
| 首次启动 | 以什么顺序启动 | 基础设施、Agent、Server、Web 的最短可靠顺序，并标明执行位置 |
| 健康检查 | 怎样判断真的可用 | 基础设施健康、Server 与 Agent 的存活/就绪语义、Web 可用性 |
| 质量门禁 | 提交前检查什么 | 引用现有四类质量入口和 GitHub Actions |
| 停止与数据 | 怎样安全收尾 | 应用退出、基础设施普通关闭、卷保留边界 |
| 延伸文档 | 去哪里看细节 | 产品、架构、开发指南、Agent 设计和决策记录 |

README 中的操作必须可以直接使用，但不包含真实凭据或个人环境值。相同命令和规则只在最合适的位置出现一次。

## 6. 任务拆分

### D1-07-A：建立 README 首次启动路径

目标：以仓库真实文件为准，形成从“理解项目”到“安全关闭”的最短完整说明。

任务：

- 从构建文件、锁文件、Compose、配置示例和健康实现核对真实入口。
- 建立 README 内容顺序，先说明跨 Windows / Ubuntu VM 的运行拓扑。
- 写明前置环境与配置准备，但不复制全部变量清单。
- 按运行依赖关系组织首次启动、健康判断、质量检查和关闭方式。
- 链接详细文档，删除重复解释和未实现能力的暗示。
- 检查 README 中没有个人地址、绝对路径、真实密钥或危险的数据重置步骤。

预期结果：README 已成为一条连续、可执行且没有隐式前提的首次启动路径。

### D1-07-B：全新启动与 Day 1 最终验收

目标：从干净项目状态只依据 README 复现 Day 1 工程底座，并收敛真实发现的问题。

任务：

- 准备不含依赖目录、构建产物和本地配置的新检出环境。
- 严格按 README 完成安全配置准备和依赖恢复。
- 在 Ubuntu VM 启动基础设施，在 Windows 启动 Agent、Server 和 Web。
- 每个阶段只使用已有的针对性健康信号判断是否继续。
- 集中执行一次既有质量门禁，不增加重复验证。
- 按 README 正常关闭应用和基础设施，确认普通关闭不删除持久化卷。
- 只修正本次复现中实际发现的 README 或开发指南偏差，然后复核受影响路径。
- 检查 Git 状态与敏感信息边界，形成 D1-07 和 Day 1 的最终验收结论。

预期结果：首次使用者无需依赖对话历史或原工作目录，即可完成安装、启动、检查和关闭。

## 8. 验收标准

### 8.1 README 完整性

- 新读者能够从 README 明确项目用途、当前完成度、三端职责和基础设施职责。
- 前置工具与版本基线准确，并明确 Windows 默认 Java 17 不被改变。
- Windows 与 Ubuntu VM 的操作位置不存在歧义。
- 配置准备覆盖根级与三端示例文件，且没有真实值、个人地址或绝对路径。
- 启动顺序与实际依赖关系一致。
- Server 和 Agent 的存活、就绪语义被正确区分，Web 不伪造服务端健康端点。
- 质量检查只复用 D1-06 已建立的入口。
- 普通关闭流程明确保留持久化卷，破坏性重置不属于日常步骤。

### 8.2 可复现性

- 从新的仓库检出开始，不借用原工作目录中的依赖、构建产物或 `.env`。
- 仅依据 README 可以恢复三端依赖并完成首次启动。
- 四项基础设施达到健康状态。
- Agent 与 Server 的存活和就绪检查符合 D1-05 契约。
- Web 开发入口可以正常响应。
- 既有四类质量门禁集中执行一次并全部通过。
- 环境可以按 README 正常关闭，持久化卷未被普通关闭删除。

### 8.3 文档与安全一致性

- README、开发指南、ADR-012、配置示例和实际工程入口不存在相互冲突。
- README 不复制长期由构建文件、锁文件和配置代码维护的细节。
- Git 中没有 `.env`、真实凭据、个人 VM 地址、本机绝对路径、依赖目录、构建产物或运行数据。
- 没有为通过验收而跳过检查、使用未记录全局依赖或降低现有安全边界。

任一首次启动步骤必须依赖对话历史、个人机器隐式状态或未记录手工操作时，D1-07 保持未完成。

## 9. 风险与处理原则

| 风险 | 影响 | 处理原则 |
| --- | --- | --- |
| README 复制开发指南 | 两处内容很快漂移 | README 保留最短路径，详细规则使用链接 |
| Windows 与 Ubuntu VM 的执行位置不清 | 命令在错误主机运行 | 每个启动区块明确运行位置，并与 ADR-012 对齐 |
| 将“全新环境”理解为删除所有数据 | 可能误删持久化卷 | 只清理项目派生产物，不执行破坏性数据重置 |
| 隐式依赖本机全局 Maven 或 Python 包 | 新检出无法复现 | 只依赖 Maven Wrapper、uv、锁文件和声明的工具 |
| JDK 21 被改成全局默认 | 破坏本机 Java 17 约束 | README 只说明项目级 Toolchains/CI 使用方式 |
| 示例配置与代码不一致 | 应用在启动期失败 | 以示例文件和真实配置读取代码交叉核对一次 |
| 首次依赖或镜像下载受网络影响 | 验收被外部波动阻塞 | 区分网络下载失败与仓库契约错误，不通过改版本绕过 |
| 为修正文档顺便重构工程 | D1-07 越界且扩大风险 | 只修正复现所需的真实偏差，工程问题单独阻塞 |
| README 描述尚未实现的业务功能 | 误导使用者 | 明确 Day 1 只完成工程骨架，链接长期产品范围 |

## 10. 阻塞条件

出现以下任一情况时暂停 D1-07：

- 当前工作区出现无法解释的用户变更。
- D1-06 合并状态或四类 CI 结果无法确认。
- README 所需入口与构建文件、锁文件、配置示例或运行代码明显冲突。
- 新检出只能依赖个人绝对路径、真实密钥或未记录的全局包运行。
- Ubuntu VM、Docker、NAT 网络或任一必要基础设施无法恢复到 D1-04 已验收状态。
- 应用必须降低 D1-05 配置或健康检查边界才能启动。
- 既有质量门禁出现与 README 无关的回归。
- 完成验收必须删除持久化卷或修改本机全局 Java 配置。

阻塞解除前，不通过修改业务代码、跳过检查、提交本地配置或弱化健康语义获得表面成功。
